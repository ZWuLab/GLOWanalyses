# GLOWanalyses settings reference

Generated by `base-config/make-settings-reference.R` from the settings registry
(`base-config/settings-registry.yml`), the table of parts (`base-config/parts.yml`), and the
workflow with its declaration file (`cloud/terra/glow_scan.wdl`,
`cloud/terra/workflow-settings.yml`). Do not edit it by hand. Regenerate it from the
GLOWanalyses directory with `Rscript base-config/make-settings-reference.R`. The image build
runs `--check` and fails when this file is stale.

A configuration is a YAML file that sets some of these settings and takes the rest from
`base-config/base_config.yml`. A setting is written under its section, for example
`snv_set:` and below it `ld_threshold: 0.8`. The three names of a run have no section. The
columns:

- **Default**: the value of `base_config.yml`. A null means that the setting is off, or that
  the workflow fills it in from the layout of the run (the description says which).
- **Read by**: the parts whose completion record depends on the setting, as `step/part`
  (`base-config/parts.yml`). `glow run <step>` runs the parts of a step in order.
- **Terra input**: the input of `glow_scan.wdl` that sets the setting. "the default" means
  that no input sets it, so the workflow runs the default. "written by the task" means that
  a task of the workflow writes its own value, with the reason. "not run by the workflow"
  marks the steps that the workflow does not run (the data preparation and the training).

## The three names of a run

| Setting | Type | Default | Read by | Terra input | Description |
|---|---|---|---|---|---|
| `dataset` | text | `example` |  | written by the task: a task names its own layout: the dataset `workflow` | The name of the dataset. It is the first folder under output_root, so every result of the dataset sits under one name. The default is the shipped synthetic example. |
| `analysis` | text | `baseline` |  | written by the task: a task names its own layout: the analysis `run` | The name of the analysis: one set of choices made on the dataset. It is the folder under the dataset. A configuration that changes a setting of a finished analysis takes a new name here. |
| `output_root` | path | `runs` |  | written by the task: the stable folder /tmp/glow/run, which every task links to its working directory | The folder under which every output is written, as <output_root>/<dataset>/<analysis>/<step>/. A relative path is read from the GLOWanalyses directory. Point it at any storage with enough room. |

## The SNV-set step (`snv_set`)

| Setting | Type | Default | Read by | Terra input | Description |
|---|---|---|---|---|---|
| `region_type` | list of: gene, window, coding, noncoding | `gene` |  | `region_type` | The kinds of SNV sets to scan, each written to a folder of its own: gene tests the variants of each gene, window tests sliding windows, coding tests each gene by coding category, and noncoding tests each gene by noncoding mask. |
| `filter_spec` | mapping | a mapping, see `base_config.yml` | `snv_set/prepare`, `snv_set/scan`, `snv_set/staar_coding`, `snv_set/staar_window` | `rare_maf_cutoff` (rare_maf_cutoff), `variant_type` (variant_type), `min_mac` (min_mac), `min_variants` (min_variants) | Which variants enter a set. qc_label and qc_pass_value name the quality-control field of the GDS file and the value that passes. variant_type is SNV, Indel or variant (both). rare_maf_cutoff is the largest minor allele frequency: 0.5 keeps the whole spectrum, which GLOW weights and collapses, and 0.01 is the choice of a rare-variant analysis. min_mac is the smallest minor allele count in the cohort. min_variants is the smallest set that is tested, and 1 keeps sets of a single variant. annotation_clauses restricts the variants by annotation: a list of clauses, of which a variant has to satisfy one. A clause maps each annotation field to the values it may take, or to a test: op in or not_in with a list of values, op gt, ge, lt or le with one number, or op nonempty or empty with no value. Values are kept as the text you write, and for an annotation that holds numbers they are compared as numbers. |

## How the work runs (`run`)

| Setting | Type | Default | Read by | Terra input | Description |
|---|---|---|---|---|---|
| `mode` | one of local, slurm | `local` |  | the default | Where `glow run` does the work. local runs the units of a step one after another in your session, which suits the example, a small study and a workflow task. slurm submits one job per unit to the SLURM scheduler and returns. |
| `records` | true or false | `true` |  | written by the task: a task runs in a container of its own, and the workflow engine keeps track of what is finished | Whether a unit of work keeps a completion record, with the lock, the overwrite guard and the checks of its inputs. Leave it true. The Terra workflow writes false into the configuration of its tasks: every task runs in a container of its own, with its inputs under new paths, and the workflow engine keeps track of what is finished. `glow run` needs the records and stops when this is false. |
| `slurm` | mapping | a mapping, see `base_config.yml` |  | the default | The settings of the SLURM mode. options is added to every sbatch call, for example "--partition=short --account=mylab". It is for the options of your site. An option that the command sets itself is refused: the job name, the log, the working directory, the dependencies, arrays, and memory, time and cores, which resources sets. Quotes keep a value with blanks together, as in --comment="my study". A job sets up R by activating the conda environment conda_env, or, when rscript is given, by calling that program, with its folder in front of PATH. setup is a list of shell lines that run before that, such as a module load. With max_queued, a call submits nothing while you have that many tasks in the queue, array tasks counted one by one, and null means no cap. The count is taken when a call looks at the queue, and one call at a time submits for a dataset: two calls for two datasets that start in the same moment can each fill the cap, so it is not a hard limit across datasets. poll_seconds is how often --wait looks at the queue. resources overrides the memory, the time limit and the cores of the jobs: a mapping from a part name, or from default for every part, to mem, time and cpus, for example {annotate_favor: {mem: 64G}, default: {time: "12:00:00"}}. A part that starts workers always asks for n_cores cores. Before it runs, a job checks that no file of the configuration changed since it was submitted, and it stops when one did. |
